# General Project Conventions

- 이 문서는 큰 프로젝트를 오래 유지보수하기 위한 공통 구조 규칙이다. 언어별 세부 규칙보다 먼저 적용한다.
- 루트 디렉토리는 얇게 유지한다. 진입 문서, 핵심 설정, 상위 폴더만 두고 기능 코드와 스크립트를 루트에 흩뿌리지 않는다.
- import 가능한 애플리케이션 코드는 전용 소스 디렉토리 아래에 둔다. Python 패키지가 커지면 `src/` 레이아웃을 우선 검토한다.
- 설정 파일은 도구가 루트 배치를 요구할 때만 루트에 둔다. 프로젝트 내부 설정 문서는 `docs/` 아래로 모은다.
- 실행 코드, 문서, 스크립트, 생성물의 경계를 섞지 않는다.
- 권장 상위 구조는 `docs/`, `src/` 또는 앱 루트, `tests/`, `scripts/` 또는 `tools/`, 생성물 디렉토리로 나눈다.
- 기능이 커지면 공용 `utils/` 하나에 몰아넣기보다 도메인 또는 feature 단위로 폴더를 나눈다.
- 같은 책임을 가진 파일은 같은 폴더에 두고, 폴더 이름만 보고도 경계가 추측되게 만든다.
- 새 폴더를 만들 때는 "런타임 경계", "도메인 경계", "배포 단위" 중 어떤 이유인지 설명 가능해야 한다.
- 임시 코드, 실험 스크립트, 마이그레이션 초안은 운영 코드와 같은 경로에 오래 두지 않는다.
- 생성 파일, 캐시, 빌드 산출물, 대용량 데이터는 소스 디렉토리와 분리하고 버전 관리 포함 여부를 명확히 한다.
- 테스트는 실제 소스 구조를 따라가게 둔다. 어느 모듈을 검증하는지 경로만 봐도 알 수 있어야 한다.
- 문서는 코드 옆에 둘지 `docs/`에 둘지 일관되게 결정하고, 두 방식을 혼용할 때는 기준을 남긴다.
- 공개 진입점 파일은 얇게 유지하고 실제 로직은 하위 모듈로 내린다.
- 순환 의존이 생기기 쉬운 공용 모듈은 특히 작게 유지하고, 기능 모듈에서 역방향 import하지 않게 설계한다.
- 파일 이름은 소문자 기반으로 일관되게 짓고, 언어별 규칙이 있으면 그 규칙을 따른다.
- 파일 하나에 여러 추상화 수준을 섞지 않는다. 라우팅, 데이터 접근, 도메인 계산, 렌더링은 가능한 한 분리한다.
- 새 기능은 "폴더를 어디에 둘지"보다 "기존 경계를 보존할 수 있는지"를 먼저 검토한다.
- 공식 가이드가 파일 총 길이 상한을 직접 주지는 않으므로, 이 프로젝트는 유지보수 정책으로 길이 제한을 둔다.
- 일반 소스 파일은 300줄 안팎을 목표로 하고, 500줄을 넘기기 전에 분할을 검토한다.
- React 컴포넌트 파일은 250줄 안팎, Python/LangGraph 구현 파일은 300줄 안팎을 넘기면 책임 분리를 먼저 검토한다.
- 500줄을 넘는 파일은 생성 코드, 스키마 집합, 긴 상수 데이터처럼 예외 사유가 있을 때만 허용한다.
- 함수도 같은 원칙을 따른다. 한 화면, 한 노드, 한 유스케이스를 설명하는 데 과하게 길어지면 하위 함수나 모듈로 내린다.
- 큰 파일을 유지해야 한다면 파일 상단에 왜 분리하지 않았는지와 어떤 경계로 읽어야 하는지 짧게 남긴다.
- 새 의존성 추가보다 기존 모듈 재구성으로 해결 가능한지 먼저 확인한다.
- 공용 모듈은 최소 API만 export하고, 내부 구현 detail은 폴더 안에 가둔다.
- 이름이 `common`, `misc`, `helper`, `temp`로 끝나는 폴더나 파일은 특별한 이유가 없으면 만들지 않는다.
- 설정, 시드 데이터, 프롬프트, 템플릿은 코드와 분리하되 너무 잘게 쪼개서 탐색 비용을 늘리지 않는다.
- 디렉토리 규칙을 어기는 예외가 생기면 코드 리뷰에서 이유와 유지 계획을 남긴다.
- 새 작업이 여러 영역을 건드리면 구조 변경과 기능 변경을 가능하면 별도 커밋 또는 별도 작업 단위로 나눈다.
